## 이번 주의 목표

2~6주차에서 Cluster Architecture, Workloads, Networking, Storage, Troubleshooting을 개별 도메인으로 익혔다. 이번 주는 **새로운 지식을 배우지 않는다.** 대신 아는 것을 "시험 시간 안에" 꺼내 쓰는 훈련을 한다.

> "CKA는 지식 시험이 아니라 속도 시험이다. 모르는 게 없어도 시간이 부족하면 떨어진다."

---

## 1. CKA 시험 형식 개괄

| 항목 | 내용 |
|---|---|
| 문항 수 | 약 15~20문제 (통상 17문제, 변동 가능) |
| 시험 시간 | 2시간 (120분) |
| 배점 | 문제마다 다름 (쉬운 문제 5~6점, 어려운 문제 10점 이상) |
| 합격 기준 | 총점 66% 이상 |
| 응시 방식 | 온라인 프록터링 (webcam + 화면 공유로 감독관이 실시간 모니터링) |
| 환경 | 브라우저 기반 통합 터미널 하나에서 여러 클러스터/컨텍스트를 오가며 문제 해결 |
| 참고자료 | kubernetes.io 공식 문서 + 공식 블로그만 열람 가능 |

### 왜 "쉬운 문제 우선"이 전략인가?

문제별 배점이 다르고, 문제 순서가 난이도순이 아니다. 즉 1번 문제가 15분짜리 고난도 문제이고 10번 문제가 2분짜리 저배점 문제일 수 있다. **점수 = 배점 × 정답 여부**이므로, 초반에 전체 문제를 훑어 "빨리 풀 수 있는 문제"부터 처리하는 것이 전체 점수를 극대화하는 방법이다.

```
[잘못된 접근]
문제 1번부터 순서대로 풀다가 3번에서 20분 소모 → 시간 부족 → 뒷문제 다 놓침

[올바른 접근]
전체 문제를 훑어 난이도 감 잡기 → 쉬운 문제부터 처리 → 어려운 문제는 flag 후 마지막에
```

## 2. 시험 중 허용되는 자료

시험 중에는 **kubernetes.io 공식 문서와 공식 블로그(kubernetes.io/blog)만** 새 브라우저 탭에서 열람할 수 있다.

- 허용: `kubernetes.io/docs/...`, `kubernetes.io/blog/...`
- 금지: Stack Overflow, 개인 블로그, GitHub 저장소, ChatGPT 등 그 외 모든 사이트
- 금지 사이트 접속이 감지되면 **부정행위로 실격** 처리될 수 있음

그래서 이번 주 실습의 핵심은 "몰라서 못 푸는 것"이 아니라 "알아도 공식 문서에서 예제를 못 찾아서 시간을 버리는 것"을 없애는 데 있다. kubernetes.io 사이트 구조 자체를 손에 익혀야 한다.

## 3. 시험 환경 커스터마이징

시험 시작 직후, 감독관 확인이 끝나면 **터미널을 자신에게 맞게 설정할 시간**이 주어진다. 이 설정은 시험 점수에 포함되지 않지만, 이후 2시간의 생산성을 크게 좌우한다.

### 왜 필요한가?

- 시험 환경의 기본 vim은 YAML 작성에 불리하다 (tab이 스페이스로 자동 변환되지 않으면 들여쓰기가 깨져 YAML 파싱 에러 발생)
- 매번 `kubectl` 전체 타이핑은 시간 낭비 — alias로 줄여야 함
- 자동완성이 꺼져 있으면 리소스 이름, 필드명을 매번 정확히 외워 타이핑해야 함

### 커스터마이징 대상

| 설정 | 목적 |
|---|---|
| `~/.vimrc` | YAML indentation을 스페이스 2칸으로 강제, 자동 들여쓰기 활성화 |
| `alias k=kubectl` | 타이핑량 절반 이하로 감소 |
| `source <(kubectl completion bash)` | 리소스/필드 자동완성 |
| `export do="--dry-run=client -o yaml"` | 자주 쓰는 플래그를 변수로 단축 |

이 설정은 시험 환경이 초기화된 상태로 시작하므로, **매번 시험 시작 시 직접 입력**해야 한다. 미리 스크립트를 암기해두거나 손에 익혀야 하는 이유다. (자세한 스크립트는 실습 노트 참고)

## 4. 시간 관리 전략

### 4-1. 문제당 평균 시간 배분

```
총 시험 시간 120분 ÷ 17문제 ≈ 문제당 평균 7분
```

이 숫자는 절대 기준이 아니라 **감각을 잡기 위한 기준선**이다. 실제로는:

- 저배점/단순 문제: 2~4분 안에 끝내야 함
- 고배점/복합 문제(멀티 리소스, Troubleshooting 등): 10~15분까지 허용
- 평균을 맞추는 것이 아니라 "쉬운 문제에서 번 시간을 어려운 문제에 재투자"하는 것이 핵심

### 4-2. 배점 높은 문제부터 처리

문제 화면에는 각 문제의 배점이 표시된다. 배점이 높은 문제(보통 etcd 백업/복구, 복합 네트워킹 구성 등)는 못 풀면 손실이 크므로, 시간이 남을 때 반드시 시도해야 한다. 반대로 저배점 문제에 20분을 쏟는 것은 비효율적이다.

### 4-3. Flag(마킹) 기능 활용

시험 UI에는 문제를 **"나중에 다시 볼 문제"로 표시(flag)**하는 기능이 있다.

```
[문제 풀이 흐름]
1번 문제 확인 → 바로 풀 수 있으면 품
2번 문제 확인 → 막히면 flag 표시 후 3번으로 이동
3번 문제 확인 → 풀 수 있으면 품
...
17번까지 한 바퀴 순회
→ flag된 문제만 모아서 재도전
→ 시간이 부족하면 flag된 문제 중 배점 높은 것부터
```

### 4-4. 막히면 넘어가는 습관

한 문제에 5분 이상 진전이 없으면 **flag하고 다음 문제로 이동**하는 것을 규칙으로 삼아야 한다. 시험 중 한 문제에 매몰되어 전체 페이스가 무너지는 것이 불합격의 가장 흔한 원인이다.

## 5. 시간을 절약하는 핵심 테크닉

### 5-1. `kubectl explain`

YAML 필드 이름이나 구조가 기억나지 않을 때, 공식 문서를 찾아 헤매는 대신 터미널에서 바로 확인한다.

```bash
kubectl explain pod.spec.containers
kubectl explain deployment.spec.strategy.rollingUpdate
kubectl explain pod.spec.affinity.nodeAffinity --recursive
```

`--recursive` 옵션을 쓰면 하위 필드까지 한 번에 트리로 출력되어, 복잡한 구조(affinity, volumes 등)를 빠르게 파악할 수 있다.

### 5-2. `--dry-run=client -o yaml`

리소스 YAML을 처음부터 손으로 타이핑하지 않고, imperative 명령으로 뼈대를 생성한 뒤 필요한 부분만 수정한다.

```bash
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml
kubectl create deployment web --image=nginx --replicas=3 --dry-run=client -o yaml > deploy.yaml
```

이 방식은 문법 오타를 원천적으로 줄여주고, 타이핑 시간을 대폭 단축한다. 생성된 YAML을 수정해서 적용하는 흐름이 CKA 시험의 기본 패턴이다.

### 5-3. `kubectl create -f - <<EOF` (heredoc)

파일을 별도로 만들지 않고, 터미널에서 바로 YAML을 입력해 리소스를 생성할 때 사용한다. 특히 공식 문서에서 예제를 복사해 붙여넣을 때 유용하다.

```bash
kubectl create -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: busybox
spec:
  containers:
  - name: busybox
    image: busybox
    command: ["sleep", "3600"]
EOF
```

공식 문서 예제를 복사 → 터미널에 붙여넣기 → EOF로 즉시 적용, 이 흐름이 파일 저장/편집보다 훨씬 빠르다.

### 5-4. 기타 단축 테크닉

| 테크닉 | 용도 |
|---|---|
| `kubectl get all -n <ns>` | 네임스페이스 내 리소스 한 번에 확인 |
| `kubectl api-resources` | 리소스 이름과 축약형(`po`, `deploy`, `svc` 등) 확인 |
| `--show-labels`, `-o wide` | 추가 정보를 빠르게 확인해 다음 명령 판단 |
| `!!` (직전 명령 재실행) | 오타 수정 후 재시도 시 시간 절약 |

## 6. 컨텍스트 전환

CKA 시험은 **여러 클러스터/컨텍스트**를 오가며 문제를 푼다. 문제마다 상단에 다음과 같은 지시가 명시된다.

```
Task weight: 4%
Set the context to `cluster1` before starting this task
```

### 왜 컨텍스트 전환을 빠뜨리면 오답 처리되는가?

각 문제는 특정 클러스터(컨텍스트)를 대상으로 채점된다. 컨텍스트를 전환하지 않고 이전 문제의 클러스터에 리소스를 생성하면, **리소스 자체는 정상적으로 만들어지지만 채점 대상 클러스터에는 존재하지 않으므로 오답 처리**된다. 즉 명령어와 YAML이 완벽해도 0점이 된다.

```bash
# 문제를 풀기 전 반드시 확인
kubectl config current-context

# 지시된 컨텍스트로 전환
kubectl config use-context cluster1

# 전환 후 다시 확인 (습관화할 것)
kubectl config get-contexts
```

이 실수는 CKA 시험에서 가장 억울하게 점수를 잃는 케이스로 꼽힌다. **문제를 읽을 때 컨텍스트 지시부터 확인 → 전환 → 확인**을 매 문제 첫 동작으로 습관화해야 한다.

## 흔한 실수

- **실수 1**: "쉬운 문제부터 풀라고 했으니 1번부터 순서대로 풀면 되겠지"
  - 정정: 문제 번호는 난이도 순서가 아니다. 전체를 먼저 훑고 배점/난이도를 파악한 뒤 순서를 재배치해야 한다.

- **실수 2**: "컨텍스트는 처음 한 번만 확인하면 된다"
  - 정정: 문제마다 대상 클러스터가 다를 수 있다. **매 문제마다** `kubectl config current-context`로 확인하는 습관을 들여야 한다.

- **실수 3**: "vimrc, alias 설정은 시간 낭비니 생략하자"
  - 정정: 설정에 드는 1~2분은 이후 118분의 생산성을 좌우한다. 특히 vim indentation 설정 없이 YAML을 직접 편집하면 들여쓰기 오류로 훨씬 많은 시간을 잃는다.

- **실수 4**: "모르는 문제는 구글링해서라도 풀어야지"
  - 정정: kubernetes.io 외 사이트 접속은 부정행위로 간주되어 실격 사유가 될 수 있다. 공식 문서 안에서 예제를 찾는 훈련이 되어 있어야 한다.

- **실수 5**: "막히면 계속 시도해서 결국 풀어야 한다"
  - 정정: 시험은 모든 문제를 다 맞히는 것이 목표가 아니라 66% 이상을 확보하는 것이 목표다. 막힌 문제에 집착하다 쉬운 문제를 놓치는 것이 더 큰 손실이다.

## 빠른 복습

- CKA는 2시간, 약 17문제, 문제별 배점이 다른 실기 시험이며 온라인 프록터링으로 진행된다.
- 시험 중 참고 가능한 자료는 kubernetes.io 공식 문서와 블로그뿐이다.
- 시험 시작 시 vimrc, alias, 자동완성을 직접 설정할 수 있고, 이는 전체 풀이 속도를 좌우한다.
- 문제당 평균 7분을 기준으로 하되, 쉬운 문제는 빨리 끝내고 어려운 문제에 시간을 재투자한다.
- `kubectl explain`, `--dry-run=client -o yaml`, heredoc(`<<EOF`)은 시험 시간을 절약하는 3대 테크닉이다.
- 문제마다 지정된 컨텍스트로 전환하지 않으면 정답을 작성해도 오답 처리된다. 매 문제 시작 전 컨텍스트 확인은 필수 습관이다.
